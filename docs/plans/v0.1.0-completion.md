## 各項的決定

### A 專案管理（看齊 Plane）

#### A1 `project-states`：自訂 State 與 Agent 階段

**現況**：`tasks.status` 是 9 個值的固定生命週期（`TASK_STATUSES`：backlog 到 done），同時代表人的進度與 Agent 的流程；合法的轉換表在 `packages/api-contract`，Server 與 Web 共用。

**行為**：
- **兩層**：
  - Task 的 **State** 由人管理，每個 Project 自訂，分屬五個群組：`backlog`、`unstarted`、`started`、`completed`、`cancelled`。
  - **Agent 階段**由系統管理，取自最新的主 Run：`planning`、`plan_gate`、`running`、`verifying`、`review_gate`、`pr_open`，沒有進行中的主 Run 時為 null。
- **預設 State**：每個群組至少一個 State，其中一個是預設。新 Project 建立「待辦、可以開始、進行中、完成、不做」五個。
- **系統觸發的轉換**移到該群組的預設 State：
  - 派工成功時，State 在 backlog 或 unstarted 群組就移到 started 的預設。
  - PR merge 或結束（沒有變更）時，移到 completed 的預設。
  - Issue 以 `not_planned` 關閉時，移到 cancelled 的預設。
  - Issue 重新打開時，移到 backlog 的預設。
- **可以派工**取代原本的 Ready：有 Repo、描述不為空或有連結的 Spec、至少一條 AC、`depends_on` 都在 completed 群組。State 在 completed 或 cancelled 群組時不能派工。
- **人工轉換**：任何時候都能改 State。有進行中的 Run 時，不能移到 completed 或 cancelled 群組。
- **Gate、Verification、Feedback Loop** 的規則改看 Agent 階段，不看 State。
- **看板**：預設依 State 分欄，可以切換成依 Agent 階段分欄（現在的看板）。
- **GitHub Issues 同步**：completed、cancelled 群組對應關閉（`completed`／`not_planned`），其他群組對應開著。

**契約**：
- **DB**：
  - 新增 `project_states`（project_id、name、color、group、position、is_default）。
  - tasks 加 `state_id`；`status` 改成 `agent_stage`（nullable enum，只剩六個 Agent 階段）。
  - migration 依舊值對應：
    - backlog → 待辦
    - ready → 可以開始
    - planning 到 pr_open → 進行中，`agent_stage` 保留原值
    - done（completed）→ 完成
    - done（not_planned）→ 不做
- **API**：
  - `GET/POST/PATCH/DELETE /api/projects/:projectId/states`
  - `Task` 加 `stateId`、`agentStage`，拿掉 `status`
  - `UpdateTaskInput` 加 `stateId`
  - 派工檢查回傳 `dispatchable: { ok, reasons[] }`
- **api-contract**：轉換表改成 Agent 階段的轉換表。

**權限**：管理 State 用 `manage_project`；改 Task 的 State 用 `edit_task`。

**錯誤**：
- 刪除使用中的 State 而沒有指定移到哪裡 → 409 `state_in_use`。
- 刪掉群組最後一個 State 或唯一的預設 → 409 `state_group_empty`。
- 有進行中的 Run 時移到 completed 或 cancelled → 409 `run_in_progress`。

**測試**：
- Server：State 與 Agent 階段的轉換表測試；migration 的對應；Issue 開關的同步。
- Playwright：看板依 State 與依 Agent 階段兩種分欄。

**完成條件**：ARCHITECTURE §5 改寫成兩層；ADR-0018；GLOSSARY 加 State、State 群組、Agent 階段；Ready 一詞在 UI 改成「可以開始」的預設 State。

#### A2 `task-properties`：優先度、日期、估計

**行為**：
- **優先度**：`urgent`、`high`、`medium`、`low`、`none`，預設 `none`。
- **日期**：開始日、截止日（日期，不含時間）。
- **估計**：Project 選一種估計方式：
  - 點數：數值
  - S／M／L 類別：值固定為 XS、S、M、L、XL
  - 不使用
- 這些欄位只存在 Orbis，不同步到 Issue。

**契約**：
- tasks 加 `priority`、`start_date`、`due_date`、`estimate`（numeric 或 text）。
- projects 加 `estimate_kind`（`points`｜`tshirt`｜`none`）。
- `Task`、`CreateTaskInput`、`UpdateTaskInput` 對應加欄位。

**錯誤**：
- 開始日晚於截止日 → 422 `invalid_date_range`。
- 估計值和 Project 的方式不符 → 422 `invalid_estimate`。

**測試**：Server 驗證；Playwright 的行內編輯。

#### A3 `task-hierarchy`：子 Task 與關係

**行為**：
- **子 Task**：
  - Task 可以有父 Task，最多 3 層，同一個 Project。
  - 父 Task 可以沒有 Repo（後端缺口 `task-without-repo`），子 Task 各自指定 Repo，符合 ADR-0011。
  - 父 Task 顯示子 Task 依 State 群組的進度。
- **關係**：
  - blocks 沿用 `depends_on`。
  - 新增 `relates_to`（雙向）與 `duplicate_of`（單向）。
  - 標成 duplicate 不會自動改 State。

**契約**：
- tasks 加 `parent_task_id`。
- 新增 `task_relations`（task_id、related_task_id、kind）。
- `Task` 加 `parentTaskId`、`childProgress`、`relations[]`。

**錯誤**：
- 形成循環 → 409 `hierarchy_cycle`。
- 超過 3 層 → 409 `hierarchy_too_deep`。
- 跨 Project → 422 `cross_project`。

**測試**：Server 的循環與深度；Playwright 的子 Task 清單與進度。

#### A4 `cycles`：Cycle

**行為**：
- **基本規則**：
  - Cycle 有名稱、開始日、結束日。
  - 同一個 Project 的 Cycle 期間不能重疊。
  - 一個 Task 同時只在一個 Cycle。
- **結束時**：未完成的 Task（不在 completed、cancelled 群組）可以一次移到下一個 Cycle，或移出 Cycle。
- **burndown**：
  - 每天記錄剩餘的 Task 數與估計總和。
  - 記錄時間是 Team 的時區的午夜，Team 設定加 `timezone`。

**契約**：
- 新增：
  - `cycles`（project_id、name、start_date、end_date、completed_at）
  - `cycle_snapshots`（cycle_id、date、remaining_count、remaining_estimate、total_count、total_estimate）
- tasks 加 `cycle_id`；teams 加 `timezone`。
- API：
  - `GET/POST/PATCH/DELETE /api/projects/:projectId/cycles`
  - `POST /api/cycles/:cycleId/complete { moveTo: cycleId | null }`

**權限**：建立與修改 Cycle、把 Task 加進 Cycle 用 `edit_task`（Member 以上）。

**錯誤**：期間重疊 → 409 `cycle_overlap`；結束日早於開始日 → 422。

**測試**：Server 的重疊、結束時移轉、每日快照（以假時鐘）；Playwright 的 Cycle 頁與 burndown。

#### A5 `modules`：Module

**行為**：
- Module 是功能群組，有名稱、負責人、狀態、開始日與目標日。
- 狀態有 `backlog`、`planned`、`in_progress`、`paused`、`completed`、`cancelled`。
- 一個 Task 可以在多個 Module。
- Module 可以連結 Repo Spec 或 Wiki 頁，顯示 Task 依 State 群組的進度。

**契約**：
- 新增 `modules`（project_id、name、lead_member_id、status、start_date、target_date、repo_spec_id、wiki_page_id）與 `module_tasks`。
- API：
  - `GET/POST/PATCH/DELETE /api/projects/:projectId/modules`
  - `PUT/DELETE /api/modules/:moduleId/tasks/:taskId`

**權限**：`edit_task`。

**測試**：Server 的多對多與進度；Playwright 的 Module 頁。

#### A6 `list-table-layout`：List 與 Table 版面

**行為**：
- **List**：分組的清單。
- **Table**：每欄一個屬性，可以行內編輯 State、優先度、負責人、日期、估計、Cycle、Module、labels。
- **批次修改**：多選後一次修改，最多 200 個 Task。

**契約**：`PATCH /api/projects/:projectId/tasks/bulk { taskIds, changes }` → `{ results: [{ taskId, ok, error? }] }`。`changes` 可以改 State、優先度、負責人、日期、Cycle，也可以加減 Module 與 labels。

**權限**：逐個 Task 檢查 `edit_task`，沒有權限的那幾個回錯誤，其他照常套用。

**錯誤**：超過 200 個 → 422 `bulk_too_large`。

**測試**：Server 的部分失敗；Playwright 的行內編輯與批次修改。

#### A7 `calendar-layout`：Calendar 版面

**行為**：
- 依截止日排在月曆上，可以拖曳改截止日。
- 在某一天快速新增時帶入該日為截止日。
- 沒有截止日的 Task 列在側欄。

**契約**：Task 查詢支援 `dueFrom`、`dueTo`（見 A9 的查詢 API）。

**測試**：Playwright。

#### A8 `timeline-layout`：Timeline 版面

**行為**：
- 依開始日與截止日畫條，`depends_on` 畫成連線。
- 拖曳條的兩端改日期，拖曳整條平移。
- 沒有日期的 Task 列在側欄，可以拖進時間軸。
- 可以依週、月、季縮放。

**效能**：500 個 Task 時捲動與拖曳順暢（虛擬化）。

**測試**：Playwright 的拖曳改日期（沿用 #90 處理 Windows 拖曳座標的寫法）。

#### A9 `views`：存檔的 View

**行為**：
- **View 的組成**：
  - 版面：board、list、table、calendar、timeline
  - 篩選、分組（一個屬性）、排序（多個）、顯示哪些欄位
- **範圍**：可以存成個人的或 Project 共用的。
- **我的工作**：跨 Project 的 View，列出指派給我、我建立的、我訂閱的 Task。

**契約**：
- 新增 `views`（project_id nullable、owner_member_id、shared、name、layout、filters jsonb、group_by、sort jsonb、display jsonb、target：`tasks`｜`wiki`）。
- 篩選的 schema 定義在 api-contract（欄位、運算子、值），自訂欄位（A11）也可以用。
- API：
  - `GET/POST/PATCH/DELETE /api/views`
  - `POST /api/projects/:projectId/tasks/query { filters, groupBy, sort, cursor }`
  - `POST /api/my-work/query`

**權限**：共用 View 由 `edit_task` 的人建立，個人 View 只有本人看得到；查詢結果套用 task-sharing。

**測試**：Server 的篩選運算子（表格測試）與權限過濾；Playwright 的存檔與切換。

#### A10 `intake`：Intake

**行為**：
- **來源集中在同一個收件匣**：
  - 登記 Repo 上新開、還沒匯入的 GitHub Issue（`issues.opened` webhook）
  - `propose_tasks` 產生的 Draft Task
  - Member 或 Viewer 在 Orbis 中提出的需求
- **處理**：
  - 接受：選 State，建立 Task；GitHub Issue 沿用現有的匯入流程。
  - 拒絕。
  - 標成重複：連到既有 Task。
  - 延後：到指定日期再出現。
- 取代現在的 Draft Task 頁。

**契約**：
- 新增 `intake_items`（project_id、source：`github_issue`｜`draft_task`｜`manual`、source_ref、title、body、status：`pending`｜`accepted`｜`declined`｜`duplicate`｜`snoozed`、snoozed_until、created_by、decided_by）。
- 既有的 draft task 資料移過來。
- API：
  - `GET /api/projects/:projectId/intake`
  - `POST /api/projects/:projectId/intake`（manual）
  - `POST /api/intake/:itemId/accept { stateId }`
  - `POST /api/intake/:itemId/decline`
  - `POST /api/intake/:itemId/duplicate { taskId }`
  - `POST /api/intake/:itemId/snooze { until }`

**權限**：提出用 `view`（Viewer 也可以）；處理用 `edit_task`。

**測試**：Server 的三種來源與四種處理（FakeGitHub 的 webhook）；Playwright 的收件匣。

#### A11 `task-types`：Task 類型與自訂欄位

**行為**：
- **Task 類型**：每個 Project 有 Task 類型，內建「Task」與「Epic」（A14）。
- **自訂欄位**：
  - 種類：文字、數字、單選、多選、日期、成員、是否
  - 可以限定只用在某個類型，可以設成必填
- 自訂欄位能在 A9 篩選與分組，不同步到 Issue。

**契約**：
- 新增：
  - `task_types`（project_id、name、icon、builtin）
  - `custom_fields`（project_id、task_type_id nullable、name、kind、options jsonb、required、position）
  - `task_field_values`（task_id、field_id、value jsonb）
- tasks 加 `type_id`。
- API：
  - `GET/POST/PATCH/DELETE /api/projects/:projectId/task-types`
  - `GET/POST/PATCH/DELETE /api/projects/:projectId/custom-fields`
  - `Task` 加 `typeId`、`fields`

**權限**：管理類型與欄位用 `manage_project`；填值用 `edit_task`。

**錯誤**：
- 必填欄位沒填 → 422 `field_required`。
- 值和種類不符 → 422 `invalid_field_value`。
- 刪除有值的欄位要確認 → 409 `field_in_use`，帶 `force` 才刪。

**測試**：Server 的各種種類驗證；Playwright 的設定頁與 Task 頁的欄位。

#### A12 `dashboards`：Dashboard 與分析

**行為**：
- **Project Dashboard**：
  - 依 State 群組的進度
  - 目前 Cycle 的 burndown
  - 每人的工作量（Task 數與估計）
  - 被卡住的 Task：等 Gate、Verification 超過上限、push 失敗、依賴沒完成
- **Agent 用量與費用**：
  - 依 Agent、Member、Project、日期彙總，原本的 N1 併入這裡。
  - Team 層級的費用只有 Admin 以上看得到。

**契約**：
- `GET /api/projects/:projectId/analytics?from&to`
- `GET /api/analytics/usage?from&to&groupBy`（Admin）
- 資料來自 H8 的活動索引與 `runs.usage`。

**權限**：Project Dashboard 用 `view`；Team 的用量用 `manage_team`。

**測試**：Server 的彙總（固定的假資料）；Playwright 的圖表與篩選。

#### A13 `task-archive`：自動封存

**行為**：
- 只有 completed、cancelled 群組的 Task 可以封存，手動或依 Project 設定自動封存。
- 自動封存的期限可選 1、3、6、12 個月，或關閉。
- 封存的 Task 不出現在看板與 View，搜尋時可以勾選包含；可以還原。

**契約**：tasks 加 `archived_at`；projects 加 `auto_archive_months`；`POST /api/tasks/:taskId/archive`、`/unarchive`；每天的排程工作。

**錯誤**：封存不在這兩個群組的 Task → 409 `task_not_closed`。

#### A14 `epics`：Epic

**行為**：
- Epic 是內建的 Task 類型，可以沒有 Repo，不能派工。
- 顯示子 Task 依 State 群組的進度與估計總和。
- Epic 頁列出子 Task，可以直接在下面建立子 Task。

**錯誤**：對 Epic 派工 → 409 `epic_not_dispatchable`。

#### A16 `agent-assignee`：Agent 當負責人

**行為**：
- **指派**：Task 的負責人之外，可以指派給一個 Agent。指派內容包括：
  - Agent
  - 在哪裡跑：Team Runner，或指派者自己的電腦
  - 模型、推理強度、權限策略：預設取 Project 的設定
- **派工**：
  - 指派後，Task 可以派工時就由系統以指派者的身分派工。
  - 還不能派工時記下原因，條件滿足時自動派工，和 N5 共用同一套規則。
- **留言**：
  - Agent 的最終回覆以 Run 為作者留成 Task 留言，過程訊息不留。
  - 權限請求照常進 Needs You。

**契約**：
- tasks 加 `agent_assignment jsonb`（agent、target、localOwnerMemberId、model、effort、permissionPolicy、assignedBy）。
- API：`PUT/DELETE /api/tasks/:taskId/agent-assignment`。

**權限**：指派者要能派工到那個目標（`dispatch_team`，或自己的 Local Runner）。

**錯誤**：Agent 在目標上不可用 → 422 `agent_unavailable`（指派仍保存，可用時再派）。

**測試**：Server 的「指派後依賴完成才派工」；Playwright 的指派與留言。

### H 給主管的彙報報表

報表的資料全部來自 Orbis 既有的紀錄，每一項都連回原始的 Task、PR 或 Run，不需要人另外填表。

#### H8 `activity-index`：活動索引

**行為**：
- **索引的內容**：依 Member 與日期彙整的活動，報表與 Dashboard 查這張表，不掃 `run_events`。
- **寫入的時機**：
  - Task 的 State 變化
  - Gate 決定
  - PR 開出與 merge：算在 Run 的派工者與 Task 的負責人
  - Run 建立與結束：結束時記下用量
  - 留言
  - Wiki 頁面編輯：同一頁每人每天一筆
  - 對話開始：只記次數
- migration 從既有資料回填。

**契約**：新增 `member_activity`（team_id、member_id、project_id、occurred_at、date、kind、ref_type、ref_id、payload jsonb）。

**測試**：Server 的各種事件寫入與回填。

#### H1 `member-report`：個人活動明細

**行為**：期間可選今天、本週、本 Cycle 或自訂，依類別列出以下內容，每項連回原始資料：
- 完成的 Task、進行中的 Task
- 合併與開著的 PR
- 核准或退回的 Gate
- 派出的 Run、開過的對話數
- Agent 用量與費用
- Wiki 頁面編輯
- 留言

**契約**：`GET /api/reports/members/:memberId?from&to&projectId`。

**權限**：見 H6。

#### H2 `team-report`：團隊總覽

**行為**：
- **每人一列**：完成、進行中、被卡住、合併的 PR、Gate、費用。
- **篩選與排序**：可以依 Project、Cycle、期間篩選，也可以排序。
- **警示**：被卡住的 Task 標成警示，原因有等 Gate、Verification 超過上限、push 失敗。
- 點一列進入 H1。

**契約**：`GET /api/reports/team?from&to&projectId&cycleId`，只回傳查看者有權限看的成員。

#### H3 `report-summary`：AI 摘要

**行為**：
- **產生方式**：
  - Server 不保存 Agent Credential（ADR-0007），所以摘要在 Runner 上產生。
  - Server 建立一個用途為報表的 Standalone Run（B1），工作位置是暫存資料夾，權限策略是 `manual`。
  - Agent 只能用 Orbis MCP 的 `get_activity` 讀這段期間的活動，寫成「做了什麼、卡在哪裡、下一步」。
  - 每句附來源連結（Task Key、PR、Run）。
- **在哪個 Runner 跑**：預設派到 Team Runner；沒有時見 D14，改派到查看者的 Local Runner。
- **保存**：摘要存下來，重新產生時保留舊版；費用算在產生的人。

**契約**：
- 新增 `report_summaries`（scope：`member`｜`team`、member_id、from、to、run_id、content、created_by）。
- API：`POST /api/reports/summaries { scope, memberId?, from, to }`、`GET /api/reports/summaries?...`。
- 協定：Run 的用途加 `report`。
- Orbis MCP 加 `get_activity`，只在 `report` 用途的 Run 中提供，而且只回傳產生者有權限看的資料。

**錯誤**：沒有可用的 Runner → 409 `no_runner_for_summary`。

**測試**：Fake Agent 劇本呼叫 `get_activity` 後回覆摘要；Server 的權限過濾。

#### H4 `report-schedule`：排程週報

**行為**：
- **設定**：Team 設定每週的星期、時間、時區。
- **寄送對象**：
  - 每位主管收到直屬下屬的報表。
  - Owner、Admin 收到團隊總覽。
- **寄送管道**：email 或 Slack（P21），同時存成 Team 的 Wiki 空間中「週報」資料夾的頁面。
- **沒有 Team Runner 時**：只寄統計，並註明沒有 AI 摘要的原因（D14）。

**契約**：teams 加 `report_schedule jsonb`；Server 的排程工作。

**測試**：Server 以假時鐘觸發，email 與 Slack 用 fake transport。

#### H5 `report-export`：匯出

`GET /api/reports/...?format=md|csv`；Markdown 可以一鍵存成 Wiki 頁（`POST /api/reports/save-to-wiki`）。

#### H6 `report-access`：彙報關係與隱私

**行為**：
- **彙報關係**：每位 Member 可以指定一位主管，必須是同一個 Team，不能形成循環。
- **誰看得到報表**：
  - 主管看得到直屬下屬的報表。
  - Owner、Admin 看得到全部。
  - 其他人只看自己的。
- **報表內容的過濾**：
  - 只列查看者本來就有權限看的 Task（套用後端缺口的 task-sharing）。
  - 對話（Standalone Run）只計次數，不顯示標題與內容，已分享給 Team 的除外。

**契約**：members 加 `manager_member_id`；`PATCH /api/team/members/:memberId { managerMemberId }`。

**權限**：設定彙報關係用 `manage_team`。

**錯誤**：形成循環 → 409 `manager_cycle`；跨 Team → 422。

**測試**：Server 的權限矩陣（本人、主管、非直屬、Admin）與內容過濾。

**文件**：ADR-0019。

#### H7 `report-notes`：本人補充與主管留言

**行為**：
- 每一期報表上，本人可以寫一段說明，例如沒有反映在 Orbis 的工作。
- 主管可以留言並 @mention，沿用留言與通知。

**契約**：新增 `report_notes`（member_id、period_start、period_end、body）；留言的 target 加 `report_note`。

### B 不經專案管理的對話

像直接用 Claude Code 或 Codex 一樣開對話叫 Agent 做事，沒有 Spec、AC 與 Gate，需要時再轉成 Task。依賴第 1 波的 `run-prompt`、`run-settings`、`agent-switch`、`terminal`、`local-repo`。

#### B1 `standalone-run`：Run 不綁 Task

**行為**：
- Standalone Run 屬於 Team，Project 與 Repo 可選。
- 有標題，預設取第一則訊息的前 60 字，可以改。
- 擁有者是建立的人。

**契約**：
- runs 的 `task_id` 改為可以是 null。
- runs 加 `kind`（`task`｜`standalone`）、`purpose`（`conversation`｜`report`）、`title`、`team_id`、`project_id`、`repo_id`、`visibility`（`private`｜`team_view`）。
- check constraint：`kind = 'task'` 時 `task_id` 不為 null。
- API：
  - `POST /api/runs { target, agent, model?, effort?, permissionPolicy, workspace, prompt }`
  - `GET /api/runs?kind=standalone&mine=true&q`

**測試**：Server 的建立、列表、constraint。

#### B2 `run-workspace`：三種工作位置

**行為**：
- **Repo 的新 Worktree（預設）**：
  - 照 §6.2 開 Worktree 與分支。
  - 分支名稱是 `orbis/run-<run id 前 8 碼>-<slug>`。
- **本機資料夾**：
  - 直接在資料夾中工作，不開 Worktree。只限 Local Runner。
  - 資料夾要先在 Desktop 加入允許清單：選資料夾時正規化路徑，拒絕家目錄本身、磁碟根目錄、Worktree 根目錄。
  - Permission Policy 的「Worktree 內」改成「這個資料夾內」。
  - 不能選 `yolo`。
  - Run 結束不刪除任何東西。
- **暫存資料夾**：
  - Runner 在狀態目錄開空的資料夾，封存時刪除。
  - Team Runner 也可以用。

**契約**：
- 協定：`DispatchOffer` 的 repo 欄位改成 `workspace`：
  - `{ kind: repo_worktree, repo, base_ref }`
  - `{ kind: local_folder, folder_id }`
  - `{ kind: scratch }`
- 資料夾的路徑只存在 Runner 的狀態目錄，Server 只知道 `folder_id` 與顯示名稱，比照本機 Repo。
- Runner 在 `AgentAvailability` 旁回報 `folders: [{ id, name }]`。
- Desktop bridge 加 `addAllowedFolder()`、`removeAllowedFolder(id)`。

**錯誤**：
- 本機資料夾用在 Team Runner → 422 `workspace_unsupported`。
- 資料夾已不在允許清單 → Runner 以 `workspace_not_allowed` 拒絕派工。
- 本機資料夾選 `yolo` → 422 `policy_not_allowed`。

**測試**：
- Runner：真實 git 與 Fake Agent 跑三種工作位置；路徑含空白與中文；資料夾外的寫入問人。
- Desktop：允許清單的路徑檢查。

**文件**：ADR-0020；ARCHITECTURE §6.2、§8。

#### B3 `conversation-loop`：對話迴圈

**行為**：
- **回合結束時**：
  - Run 進入新的狀態 `awaiting_input`，不送 Review Gate、不跑 Verification。
  - 有排隊的訊息（`run-prompt`）就直接開始下一回合。
- **Runner 或 Desktop 重新啟動後**：Run 停在 `awaiting_input`；下一則訊息送出時，Runner 以 `session/resume`（或 `session/load`）接回原本的 session，不支援時開新的 session，附上交接 prompt（沿用 `agent-switch` 的格式）。
- **閒置**：預設 7 天沒有訊息就結束 Run。

**契約**：
- RunStatus 加 `awaiting_input`。
- 協定：Runner 對 Standalone Run 的回合結束送 `awaiting_input` Event，不送 diff。
- 差異分頁需要時以 RunControl `get_diff` 取得 diff。

**測試**：Fake Agent 劇本：連續三回合、重啟後接回 session、不支援 resume 時的交接 prompt。

#### B4 `run-finish-actions`：收尾動作

**行為**：差異分頁提供以下動作：
- **commit**：可以填訊息。
- **push 並開 PR**：限 GitHub Repo，經 GitHub App 開 PR；PR 不連到 Task，也沒有 Feedback Loop。
- **本機合併**：限本機 Repo，沿用 `MergeLocal`。
- **捨棄**：取消並封存。

**契約**：RunControl 加 `Commit { message }`、`PushAndOpenPr { title, body }`、`Discard`；本機合併沿用 `MergeLocal`。

**錯誤**：
- 工作位置不支援該動作 → 422 `action_unsupported`。
- 本機資料夾只能 commit。

**測試**：Runner 的四種動作（真實 git）；Server 開 PR（FakeGitHub）。

#### B5 `promote-to-task`：轉成 Task

**行為**：
- **草擬 Task**：Server 對 Run 送一則固定的 prompt，請 Agent 以 Orbis MCP 的 `draft_task_from_run` 回報標題、描述、AC 草稿。
- **建立 Task**：人在對話框中編輯後建立。這個 Run 改成 `kind = task` 並掛上新的 Task。
- **進入完整流程**：Runner 送出 diff 並進入 Review Gate，之後走完整流程。

**契約**：
- API：`POST /api/runs/:runId/promote/draft` → `{ draftId }`。
- 草稿完成後經 ws 推送。
- API：`POST /api/runs/:runId/promote { projectId, title, description, acceptanceCriteria, stateId }`。

**錯誤**：工作位置不是 Repo Worktree → 409 `workspace_not_promotable`。

**測試**：Fake Agent 劇本回報草稿；完整系統 e2e：對話轉成 Task 到核准。

#### B6 `conversation-ui`：對話的 UI

**行為**：
- **側欄**：「對話」區塊列出自己的對話，依最後活動排序。
- **建立**：Ctrl+N 開新對話。
- **工作區**：畫面沿用 Run 工作區，上方顯示工作位置。
- **其他**：搜尋（N2）、封存、接續舊對話。
- **需要處理時**：權限請求出現在 Needs You，側欄的對話標出未讀。

**測試**：Playwright 的建立、送出、收尾、轉成 Task。

#### B7 `conversation-access`：對話的權限與分享

**行為**：
- **可見範圍**：預設只有建立者看得到；可以分享給 Team 唯讀（`team_view`）。
- **權限請求**：只有擁有者能回覆。
- **在 Team Runner 上開對話**：
  - 要 Member 以上。
  - 有指定 Project 時，要該 Project 的 `dispatch_team`。
- 彙報報表（H6）只計次數，已分享的除外。

**測試**：Server 的權限矩陣。

### W Wiki（參考 Obsidian）

Obsidian 的 vault 是一個資料夾裡的 Markdown 檔，coding agent 最擅長處理這種形式。Orbis 的 Wiki 採用同一套檔案格式與連結模型，權限與共同編輯沿用 Plane 的做法。

#### W1 `wiki-vault`：vault 結構

**行為**：
- **空間與頁面**：
  - 每個 Wiki 空間就是一個 vault：Team 一個、每個 Project 一個。
  - 資料夾就是 Collection。
  - 頁面是 `.md` 檔，屬性寫在 YAML frontmatter。
  - 附件放在空間的 `attachments/` 資料夾。
- **以 Markdown 原文為準**：
  - 儲存以 Markdown 原文為準，Yjs 快照只是編輯中的狀態。
  - 共同編輯沿用 §12.1：debounce 1 秒寫回原文。
  - 原文被匯入、git 同步或 API 改掉時，以新內容更新文件。
- 頁面路徑在空間內唯一，檔名不能含 `\ / : * ? " < > |`，Windows 與 Obsidian 都不接受這些字元。

**契約**：
- 新增：
  - `wiki_spaces`（team_id、project_id nullable、name）
  - `wiki_folders`（space_id、parent_id、name）
  - `wiki_pages`（space_id、folder_id、path、title、markdown、frontmatter jsonb、yjs_snapshot、private_owner_member_id、updated_by、updated_at）
- 附件是 blob，不套用保存期限（`expires_at` 為 null）。
- API：
  - `GET /api/wiki/spaces`
  - `GET/POST/PATCH/DELETE /api/wiki/spaces/:spaceId/folders`
  - `GET/POST/PATCH/DELETE /api/wiki/pages`
  - 共同編輯的 ws 沿用 collab。

**測試**：Server 的路徑規則、Markdown 與 Yjs 互轉（含 frontmatter、wikilink、嵌入的保真）；Playwright 的頁面樹。

**文件**：ADR-0021；GLOSSARY 加 Wiki 空間、vault。

#### W2 `wiki-links`：雙向連結

**行為**：
- **語法**：`[[頁面]]`、`[[頁面#標題]]`、`[[頁面|別名]]`，輸入 `[[` 時自動完成。
- **改名或移動時**：Server 改寫所有連到它的頁面，以系統的身分編輯，在版本紀錄中標出。
- **連到 Orbis 的物件**：`[[ORB-12]]` 連到 Task，`[[skill:名稱]]` 連到 Skill，`[[run:<id>]]` 連到 Run 或對話。

**契約**：
- 新增 `wiki_links`（source_page_id、target_page_id nullable、target_text、kind：`link`｜`embed`、heading、block_id、target_type：`page`｜`task`｜`skill`｜`run`、target_ref）。
- 存檔時解析並重建這張表。

**測試**：Server 的解析、改名改寫、斷掉的連結。

#### W3 `wiki-backlinks`：反向連結與未連結的提及

**行為**：
- **反向連結**：頁面側欄列出所有連到它的頁面與上下文。
- **未連結的提及**：其他頁面中出現這頁的標題或 frontmatter 的 `aliases`、卻沒有加連結的地方，可以一鍵轉成連結。
- **Task 頁**：列出提到它的 Wiki 頁。

**契約**：`GET /api/wiki/pages/:pageId/backlinks`、`GET /api/wiki/pages/:pageId/unlinked-mentions`（用 N2 的全文索引）；`GET /api/tasks/:taskId/wiki-mentions`。

#### W4 `wiki-embeds`：嵌入與區塊參照

**行為**：
- **語法**：`![[頁面]]`、`![[頁面#標題]]`、`![[圖片.png]]` 嵌入顯示；段落結尾的 `^id` 是區塊 ID，`![[頁面#^id]]` 嵌入那一段。
- **權限**：嵌入的頁面沒有權限時顯示「沒有權限」。
- **限制**：嵌入最多 3 層，避免循環。

**測試**：Playwright 的嵌入顯示與循環。

#### W5 `wiki-properties`：Tag、Properties 與頁面檢視

**行為**：
- **Tag**：`#tag` 與 frontmatter 的 `tags` 都算 tag。
- **Properties 的型別**：
  - 每個空間記住每個屬性的型別：文字、數字、日期、清單、成員、是否。
  - 第一次使用時推斷，Obsidian 也是這樣。
- **頁面檢視**：
  - 比照 Obsidian Bases，依屬性篩選、排序、分組（一個屬性）。
  - 版面有 table、list、cards，沿用 A9 的 View（`target = wiki`）。

**契約**：新增 `wiki_property_types`（space_id、name、kind）；頁面查詢 `POST /api/wiki/spaces/:spaceId/pages/query`。

**測試**：Server 的屬性型別推斷與查詢；Playwright 的檢視。

#### W6 `wiki-graph`：Graph view

**行為**：
- **範圍**：整個空間的關聯圖，以及單頁的局部圖（深度 1 或 2）。
- **操作**：可以依 tag、資料夾篩選，點節點開頁面。
- **上限**：超過 2,000 個節點時只顯示連結最多的 2,000 個。

**契約**：`GET /api/wiki/spaces/:spaceId/graph`、`GET /api/wiki/pages/:pageId/graph?depth=`。

#### W7 `wiki-collab`：共同編輯、版本、留言、範本

**行為**：
- **版本紀錄**：
  - 閒置 1 分鐘或每 10 分鐘存一個版本。
  - 可以比較任兩版、還原。
- **留言與 @mention**：頁面留言與 @mention 沿用留言與通知（§12.3）。
- **頁面範本**：沿用 N3 的範本。

**契約**：新增 `wiki_page_versions`（page_id、markdown、created_by、created_at）；留言的 target 加 `wiki_page`。

#### W8 `wiki-access`：資料夾權限

**行為**：
- **預設權限**：
  - Project 空間：Member 以上可以 Edit，Viewer 可以 View。
  - Team 空間：Member 以上可以 Edit。
- **資料夾權限**：
  - 資料夾可以設定 View、Comment、Edit，對象是成員或 Role。
  - 子資料夾與頁面繼承，可以在子資料夾再調整。
- **私人頁**：只有擁有者看得到。
- **Owner、Admin**：永遠有完整權限。

**契約**：新增 `wiki_folder_permissions`（folder_id、subject_type：`member`｜`role`、subject、level）；`authorize()` 加 Wiki 這一層。

**測試**：Server 的權限繼承矩陣。

#### W9 `wiki-agent-access`：Agent 讀寫 Wiki

**行為**：
- **快照**：
  - Runner 把這個 Run 的派工者有權限讀的空間，放進工作位置的 `.orbis/wiki/<空間>/`。
  - Repo Worktree、暫存資料夾、consult Run 都放，本機資料夾工作時不放，避免寫進使用者的資料夾。
  - 快照預設不含附件。
- **不進 diff**：Runner 在 diff 與自動 commit 時排除 `.orbis/wiki/`，和 K4 的 Skill 一樣。
- **Agent 的修改**：每個回合結束時，Runner 比對快照，Agent 改過的檔案以 `tool_call` 回報，由 Server 建立「建議修改」，人在 Wiki 中接受或拒絕。
- **讀最新內容**：另外提供 Orbis MCP 的 `search_wiki`、`read_wiki_page`，查快照以外的最新內容。

**契約**：
- 協定：`DispatchOffer.wiki: [{ space_id, name, bundle_url, sha256 }]`；Runner 以 `tool_call` 的 `propose_wiki_edits` 回報修改。
- DB：新增 `wiki_suggestions`（page_id、run_id、base_markdown、proposed_markdown、status）。
- 快照的 bundle 在 Server 端依權限產生，網址短效。

**測試**：Runner：Fake Agent 改快照中的檔案 → 回報建議；diff 不含 `.orbis/wiki/`。Server：權限過濾與接受建議。

#### W10 `wiki-import-export`：匯入與匯出 vault

**行為**：
- **匯出**：zip，保留資料夾、連結、附件、frontmatter，可以直接用 Obsidian 打開。
- **匯入**：
  - 忽略 `.obsidian/`。
  - 同名頁面可選略過或覆蓋。
  - zip 的檢查和 K1 相同：路徑穿越、symlink、大小與壓縮比。

**契約**：`GET /api/wiki/spaces/:spaceId/export`、`POST /api/wiki/spaces/:spaceId/import`。

#### W11 `wiki-git-sync`：Git 雙向同步

**行為**：
- **設定**：
  - 每個空間可選，預設關閉。
  - 開啟時指定一個 Repo、分支與路徑。
  - 以 Orbis 中的 Markdown 原文為準，git repo 是同步的對象（D12）。
- **Orbis 到 git**：
  - 頁面閒置 30 秒後 commit。
  - GitHub Repo 經 GitHub App 寫入。
  - 本機 Repo 經擁有者的 Local Runner 寫入，那台 Runner 離線時排隊。
- **git 到 Orbis**：
  - push 經 webhook（本機 Repo 由 Runner 偵測）拉回變更的 `.md`。
  - 以上次同步的內容為 base 做三方合併。
  - 能合併時以 Yjs 更新套進文件。
  - 不能合併時保留 Orbis 的版本，另外建立「<頁名>（衝突 <日期>）」頁，存 git 的內容，並通知最後編輯的人。
- **忽略**：`.obsidian/` 與 `.trash/`。
- **使用 Obsidian 的人**：搭配 Obsidian Git 外掛就能和 Orbis 雙向同步。

**契約**：
- 新增 `wiki_git_sync`（space_id、repo_id、branch、path、last_synced_commit、status）。
- RunControl 加 `WikiSync { push, pull }`，給本機 Repo 用。

**權限**：開啟與設定用 `manage_project`（Team 空間用 `manage_team`）。

**錯誤**：Repo 沒有安裝 GitHub App → 409 `repo_not_connected`；分支被保護無法寫入 → 同步狀態改成錯誤並通知。

**測試**：Server：三方合併的成功與衝突（FakeGitHub）。Runner：本機 Repo 的同步（真實 git）。

#### W12 `wiki-to-repo-spec`：頁面提交成 Repo Spec

沿用 §12.1 的「提交到 repo」，來源從 Spec 草稿改成 Wiki 頁。提交後頁面記下對應的 Repo Spec 與版本。

### K Skills

Skill 的格式採 agentskills.io 的 SKILL.md，各家 Agent 都支援；不改成各家互不相容的 plugin 格式。

#### K1 `skill-library`：Skill 庫與版本

**行為**：
- **建立**：上傳資料夾或 zip，或在 UI 編輯 SKILL.md 與附帶檔案；可以分類。
- **驗證**：
  - `name` 必須等於目錄名稱，只能用小寫字母、數字與 `-`。
  - 不能用 `anthropic`、`claude` 等保留字。
  - `description` 必填。
- **zip 檢查**：路徑穿越、指向外部的 symlink、單檔與總大小上限（10 MiB／50 MiB）、壓縮比上限（100 倍）。
- **版本**：
  - 每次儲存就是一個新版本，版本不可變。
  - 記下逐檔 sha256 清單，格式比照 MCP SEP-2640。

**契約**：
- 新增：
  - `skills`（team_id、owner_member_id nullable、name、description、category）
  - `skill_versions`（skill_id、version、manifest jsonb、bundle_blob_id、scan jsonb、requires_approval、approved_by、approved_at、source jsonb、created_by）
- bundle 不套用保存期限。
- API：
  - `GET/POST /api/skills`
  - `GET/PATCH/DELETE /api/skills/:skillId`
  - `POST /api/skills/:skillId/versions`
  - `GET /api/skills/:skillId/versions/:version`

**測試**：Server 的名稱驗證與 zip 防護（惡意 zip 的 fixture）。

**文件**：ADR-0022；GLOSSARY 加 Skill、Skill 版本、個人 Skill。

#### K2 `skill-approval`：靜態掃描與核准

**行為**：
- **掃描**：每個版本儲存時靜態掃描，出現以下任一項就要 Admin 核准：
  - `scripts/` 或可執行檔
  - SKILL.md 中的 `` !`cmd` ``
  - `hooks`、`allowed-tools`
  - 網址、MCP 引用
  - 像憑證的字串
- **審核者**不能是這個版本的作者。審核畫面列出所有檔案、digest 與掃描結果。
- **綁定**：核准綁在 sha256 清單上，同一個版本加入其他 Project 不用再核准。
- **Team Runner 上**：一律要核准（D8）。

**契約**：`POST /api/skills/:skillId/versions/:version/approve`、`/reject`；Needs You 加種類 `skill_approval`。

**權限**：核准用 `manage_team`，而且不能是作者。

**錯誤**：作者核准自己的版本 → 403 `self_approval`。

**測試**：Server 的掃描規則（每種觸發條件各一個 fixture）與自我核准。

#### K3 `skill-project`：加入專案

**行為**：
- **加入**：在 Skill 庫或 Project 設定都能把 Skill 加入 Project，加入時固定版本；Skill 庫出新版時提示更新。
- **載入**：Project 內的 Run 一律載入。
- **個別調整**：Task 與 Run 可以個別關閉，或追加 Team 庫中的其他 Skill。
- **數量警告**：一個 Run 載入超過 15 個 Skill 時警告。Codex 預設只給 Skill 清單約 2% 的 context。

**契約**：新增 `project_skills`（project_id、skill_id、version）、`task_skill_overrides`（task_id、skill_id、enabled、version）；`CreateRunInput.skills`。

**權限**：不需要核准的版本，Member 可以加入；需要核准而還沒核准的版本不能加入。

**錯誤**：未核准 → 409 `skill_not_approved`。

#### K4 `skill-injection`：注入

**行為**：
- **下載**：Runner 依 `DispatchOffer.skills` 下載 bundle，網址短效，驗證 sha256 後原子替換到位。
- **寫入位置**：依 Agent Profile 寫進一個專案路徑：
  - Claude Code：`.claude/skills/`
  - Codex、Antigravity：`.agents/skills/`
  - Grok Build：`.grok/skills/`
- **不支援 Skill 的 Agent**：改由 Orbis MCP 提供 `skills/list`、`skills/get`（對齊 SEP-2640），內容標示來源，當成不受信任的輸入。
- **不用 `.git/info/exclude`**：linked worktree 和主 repo 共用這個檔案，會影響使用者自己的 checkout。改由 Runner 在 diff 與自動 commit 時排除注入的路徑。
- **同名 Skill**：repo 已有同名 Skill 時不注入，在 Run 中記下。
- **使用者層級的同名 Skill**：配合 G1 隔離使用者層級的 Skill 目錄，避免同名的個人 Skill 蓋過固定版本。Claude Code 是個人層級優先。
- **Team Runner**：在 Claude Code 的 managed settings 開啟 `disableSkillShellExecution` 與 `allowManagedPermissionRulesOnly`。

**契約**：
- 協定：`DispatchOffer.skills: [{ name, version, sha256, bundle_url }]`。
- Agent Profile 加 `skills_project_path`（`.claude/skills`｜`.agents/skills`｜`.grok/skills`｜none）。

**測試**：Runner：
- 四個 Agent 設定檔的注入路徑。
- diff 與自動 commit 不含注入的檔案。
- 同名略過。
- sha256 不符時拒絕。

#### K5 `skill-repo-sync`：從 GitHub repo 同步

**行為**：
- 指定 GitHub repo 與路徑，push 時經 webhook 建新版本。
- 版本記下 repo、commit sha、路徑。
- 新版本照樣走 K2；已加入 Project 的固定版本不自動更新。

**契約**：新增 `skill_sources`（skill_id、repo_id、path、last_commit）。

#### K6 `skill-usage`：使用紀錄

**行為**：
- **載入紀錄**：每個 Run 載入了哪些 Skill 的哪個版本，寫進稽核紀錄（N4）。
- **repo 內既有的 Skill**：Run 開始時掃描 repo 內本來就有的 Skill，記下路徑與 hash。這些 Skill 沒有經過 Orbis 的核准，Run 的資訊中標示出來。

**契約**：新增 `run_skills`（run_id、skill_version_id nullable、source：`orbis`｜`repo`、path、sha256）；Runner 以 Event `skills_loaded` 回報。

#### K7 `skill-to-repo`：提交到 Repo

**行為**：
- **寫入路徑**：依 Project 使用的 Agent 寫進 `.claude/skills/`、`.agents/skills/`，或兩者都寫。四個 Agent 都不會同時讀兩個路徑，不會重複載入。
- **提交方式**：
  - GitHub Repo 經 GitHub App 開 PR。
  - 本機 Repo 直接 commit 到基準分支。
  - 沿用 §12.1 的流程。
- **之後**：合併後 Runner 直接從 base commit 讀，不再注入。
- **repo 中的 Skill 被人改過時**：更新的 PR 預設保留 repo 的版本並列出差異，比照 Orca 的 Keep local。

**契約**：`POST /api/skills/:skillId/versions/:version/commit-to-repo { repoId, paths }`。

**權限**：`edit_task`，而且版本已核准或不需要核准。

#### K8 `personal-skills`：個人 Skill

只在擁有者自己派工或開對話的 Run 中載入，不經 Admin 核准，不能加入 Project；Team Runner 上不載入。`skills.owner_member_id` 不為 null 就是個人 Skill。

#### K9 `skill-drafts`：從 Run 產生 Skill 草稿

**行為**：
- **產生**：Run 結束後，可以在 Run 工作區按「整理成 Skill」。Server 送一則固定的 prompt，Agent 以 Orbis MCP 的 `draft_skill` 回報 SKILL.md 與附帶檔案。
- **收進庫**：草稿由人編輯後才收進 Skill 庫，預設是個人 Skill。
- **說明**：Skill 的說明可以連到 Wiki 頁（`[[skill:名稱]]` 反向也成立）。

**契約**：新增 `skill_drafts`（run_id、content jsonb、status）；Orbis MCP 加 `draft_skill`。

### R 執行環境隔離

Team Runner 在八項業界共同做法中，五項不符合、三項部分符合：

| 業界共同做法 | Team Runner 現況 | 對應 |
|---|---|---|
| 每個任務一個一次性環境 | 所有 Run 共用一個長期執行的容器 | R1 |
| 預設拒絕外連，只開白名單 | 沒有限制 | R2 |
| Credential 不進沙盒，由外部 proxy 注入 | 全部 Credential 以環境變數給每個 Agent 子程序 | R3、R4 |
| git push 在沙盒外，token 短效且限定 Repo | push 由 Runner 執行，但 PAT 長效且 Agent 讀得到 | R5 |
| setup 與 Agent 階段分開 | 同一個容器、同一組環境變數 | R6 |
| 每個任務有資源上限 | 只有 `shm_size` | R7 |
| 依賴固定在 image，setup 後存快照 | ACP adapter 在第一次派工時用 npm 安裝 | R8 |
| 封鎖 metadata 端點，外連可稽核 | 沒有 | R2、R9 |

新架構分成三部分：
- **控制容器**：跑 orbis-runner，負責連線、Permission Policy、git push、發 token。
- **每個 Run 一個 worker 容器**：Agent、setup、verify、Preview 在這裡跑，裡面沒有 Credential，不能直接外連。
- **egress proxy**：依白名單放行外連。

#### R1 `run-container`：每個 Run 一個 worker 容器

**行為**：
- **容器的設定**：
  - `runner.toml` 的 `[sandbox] mode = "container"` 時，每個 Run 開一個 worker 容器。
  - 容器設定：`--rm`、唯讀根目錄、`cap_drop: ALL`、`no-new-privileges`、非 root。
  - 可選 gVisor（`runtime = "runsc"`）。
- **掛載**：Worktree 以 bind mount 掛到 `/work`；Runner 的狀態目錄不掛進去。
- **程序與 Preview**：
  - Runner 以 `docker exec -i` 啟動 Agent 並接 ACP 的 stdio。
  - setup、verify、Preview 也在同一個容器執行。
  - Preview 的轉送改連 worker 的 port。
- **生命週期**：
  - Run 結束時停止容器。
  - 封存或取消時移除容器。
  - Feedback Loop 接續時開新容器，掛同一個 Worktree。
- **docker socket**：Runner 不直接掛 docker socket，改透過 compose 中的 socket proxy 建容器。proxy 只開放 containers 的 create、start、stop、kill、remove、exec、inspect。

**契約**：
- compose 加 `docker-socket-proxy` 與 worker 用的 `internal: true` 網路。
- 協定的 `hello` 加 `sandbox: { mode, egress }`，Server 與 UI 據此顯示 Runner 的隔離等級。

**測試**：
- CI：docker API 用假的 socket proxy，確認建立容器的參數（唯讀根目錄、`cap_drop`、`no-new-privileges`、掛載）與生命週期的呼叫順序。
- 本機容器測試（見[波次與契約](#波次與契約)）：
- Run 跑完容器被移除。
- 容器內讀不到 Runner 的狀態目錄與 Credential。
- 根目錄不可寫。

**文件**：ADR-0024；修訂 ADR-0005；ARCHITECTURE §6、§16。

#### R2 `egress-proxy`：預設拒絕外連

**行為**：
- **網路**：worker 容器只連得到 egress proxy 與控制容器，沒有預設路由。
- **egress proxy**：
  - `orbis-runner egress` 子命令，同一個 image 的另一個 compose service。
  - 以 HTTP CONNECT 依 Host 放行，不終止 TLS。
- **白名單**由三份合併：
  1. Agent Profile 的必要網域，例如 `api.anthropic.com`
  2. `.orbis/config.toml` 新增的 `[network] allow`，從 base commit 讀，比照其他設定
  3. Project 設定的 `network_allow_extra`，由 Admin 維護
- **一律封鎖**：`169.254.169.254` 等 metadata 端點、私有網段（控制容器除外）。
- **被擋的請求**：
  - 寫成 Event `egress_blocked { host, port, phase }`。
  - 工作區顯示，Admin 可以一鍵加進 `network_allow_extra`。

**契約**：
- 協定：Event `egress_blocked`；控制容器以本機 socket 告訴 proxy 每個 Run 的白名單。
- DB：projects 加 `network_allow_extra`。
- config：`[network] allow`、`setup_allow`（R6）。

**測試**：
- CI：egress proxy 以一般程序執行，測白名單的合併、CONNECT 的放行與拒絕、metadata 端點與私有網段的封鎖、`egress_blocked` Event。
- 本機容器測試：worker 容器只能經由 proxy 外連。

#### R3 `credential-scoping`：Credential 最小化

**行為**：
- **只給需要的 Credential**：
  - Runner 只把這個 Run 選定的那一組 Credential 交給 Agent 子程序。
  - 環境變數改成白名單：PATH、HOME、LANG 等加上該 Credential 的變數。
- **Codex**：`auth.json` 每個 Run 複製一份到該 Run 專屬的 `CODEX_HOME`，配合 G1，Run 結束即刪。
- **Team Runner**：entrypoint 不再把 `agent_credentials` 匯出成整個程序的環境變數，改成交給 Runner 依 Credential 分組保存在記憶體。
- 現有的單一容器就能先做，排在第 2 波。

**契約**：`deploy/secrets/agent_credentials` 的格式加上 Credential 分組，例如 `[claude-code]` 區段；舊格式視為一組。

**測試**：Runner：Fake Agent 印出環境變數，確認只有選定的 Credential；Run 結束後 auth 副本被刪除。

#### R4 `credential-proxy`：Credential 由 proxy 注入（驗證後才做）

**驗證**：R1、R2 完成後，以 Claude Code 與 Codex 實機驗證「worker 內只有 placeholder，proxy 終止 TLS 後換成真值」是否可行，結果寫進 ARCHITECTURE。驗證需要的條件：
- worker 信任自簽 CA
- Agent 的 OAuth 重新整理流程不壞掉

**行為**（可行時）：
- egress proxy 對 Agent Profile 標記的模型網域終止 TLS，把 placeholder 換成 Credential。
- worker 內不再有任何 Credential。

**錯誤**：驗證不可行的 Agent 維持 R3，AgentAvailability 標出隔離等級。

#### R5 `push-token`：Runner 端的短效 push token

**行為**：
- **發 token**：Team Runner 要 fetch 或 push 時，向 Server 要一張 GitHub App installation token，限定這個 Repo；push 用 `contents: write`，fetch 用 `contents: read`。
- **使用**：
  - token 以 `GIT_ASKPASS` 腳本取用，腳本放在 Runner 的暫存目錄，用完即刪。
  - token 不進 Agent 的環境。
- **只推 Run 自己的分支**：Runner 以明確的 refspec push，不帶 `--force`。
- **Local Runner**：維持使用者自己的 git 憑證。
- 取代 `deploy/secrets/github_token` 的 PAT；舊的 secret 保留一個版本作為退路，之後移除。
- 現有的單一容器就能先做，排在第 2 波。

**契約**：
- `POST /api/runner/git-token { runId, access: read|write }` → `{ token, expiresAt }`。
- 以 Runner token 認證，只能為自己正在執行的 Run 要 token。

**錯誤**：GitHub App 沒有安裝在這個 Repo → 409 `repo_not_connected`，Run 以 `push_failed` 停下。

**測試**：Server：token 的範圍與 Runner 驗證（FakeGitHub）。Runner：askpass 腳本用完即刪；Agent 的環境中沒有 token。

**文件**：ADR-0017；ARCHITECTURE §11。

#### R6 `setup-phase`：setup 與 Agent 分兩段

**行為**：
- **setup 階段**：
  - 只放行 `[network] setup_allow`，預設是常見的套件 registry。
  - 可以拿 build secret。
- **Agent 與 verify 階段**：用 `[network] allow`，看不到 build secret。
- **build secret**：放在 Team Runner 的 Docker secret `build_secrets`，以 `runner.toml` 的 `[repos.<key>] build_secrets = ["NPM_TOKEN"]` 指定哪些 Repo 可以用。Server 不保存，符合 ADR-0007。

**測試**：CI 測兩階段的環境變數與白名單組合；本機容器測試確認 setup 讀得到 build secret、Agent 階段讀不到。

#### R7 `run-limits`：資源上限

**行為**：
- `runner.toml` 的 `[sandbox]` 設定 `memory`（預設 `4g`）、`cpus`（預設 2）、`pids`（預設 1024）。
- 超過記憶體時容器被 OOM kill，Run 以 `resource_limit` 失敗並顯示原因。

#### R8 `worker-image`：worker image 與快取

**行為**：
- **worker image**：
  - `orbis-worker` 預裝固定版本的 Agent adapter：claude-agent-acp、codex-acp、agy_acp_server（比對 sha256），以及 git。
  - Team Runner 不再在派工時用 npm 安裝。
- **套件快取**：依 Repo 共用 volume（npm、pnpm store、cargo registry）。
- **setup 快照**：
  - `[worktree] snapshot = true` 時，setup 成功後把容器存成 image。
  - key 是 Repo、設定檔 hash、lockfile hash。
  - 之後的 Run 直接用，每個 Repo 保留最近 5 個。
- **image 不含任何身分**：不含 Runner 身分或登入資料，比照 Orca 的 base 與 auth 分層。

**契約**：`crates/runner/Dockerfile.worker`；P4 一併發布到 GHCR。

#### R9 `sandbox-audit`：隔離的稽核

egress proxy 的放行與拒絕、每個 Run 發出的 token（只記範圍與時間，不記內容）寫成 Event，並寫進稽核紀錄（N4）。

#### R10 `sandbox-provider`：可替換的 provider

**行為**：
- **腳本契約**：比照 Orca 的 environment recipe，`runner.toml` 的 `[sandbox.provider]` 以四個腳本定義 worker 環境：
  - `create`：只在 stdout 印一個 JSON，包含 exec 指令、工作目錄、Preview 的 host 與 port、環境 ID
  - `suspend`、`resume`：從 stdin 讀環境 ID
  - `destroy`：一定要有
- **內建 provider**：只有本機 Docker，也實作同一個介面。
- **檢查**：
  - `orbis-runner sandbox doctor`：靜態檢查。
  - `orbis-runner sandbox doctor --provision`：實際建立、驗證、銷毀一次。

**測試**：以假的 provider 腳本測試四個步驟與錯誤輸出（Windows 與 macOS 都跑，不需要 Docker）。

#### R11 `team-yolo`：Team Runner 的 yolo

**行為**：
- Runner 回報 `sandbox.mode = container` 而且 egress 開啟時，Team Runner 才能選 `yolo`，派工對話框照樣顯示警告。
- R3、R5 未完成的 Runner 不能選。

**錯誤**：不符合條件 → 422 `policy_not_allowed`。

#### R12 `env-scrub`：Local Runner 清理環境變數

**行為**：
- **移除的變數**：Agent 子程序不繼承以下變數：
  - `GH_TOKEN`、`GITHUB_TOKEN`、`GH_ENTERPRISE_TOKEN`
  - `AWS_*`、`AZURE_*`、`GOOGLE_APPLICATION_CREDENTIALS`
  - `NPM_TOKEN`
  - 其他 Agent 的 API key：例如 Codex 的 Run 拿不到 `ANTHROPIC_API_KEY`
- **保留清單**：`runner.toml` 的 `[env] keep` 可以保留特定變數。
- **Windows**：變數名稱不分大小寫，比對時要一併處理。
- **push**：一律由 Runner 執行。

**測試**：Runner：Fake Agent 印出環境變數，確認被移除；Windows 的大小寫。

#### R13 `local-container`：Local Runner 的選用容器模式

**行為**：
- **開啟條件**：有 Docker Desktop 時，可以在 Desktop 設定或 `runner.toml` 開啟容器模式，Run 改在和 Team Runner 相同的 worker 容器中執行。
- **Windows**：
  - 需要 Linux 容器（WSL2 後端）。
  - Worktree 在 Windows 磁碟時以 bind mount 掛入，效能較差，設定頁提示。
- **登入資料**：每個 Run 複製一份（R3）。

**測試**：共用 R1 的本機容器測試；Desktop 的設定開關在 CI 測。

### P Phase 2 清單

#### P2 `team-runner-agents`：Team Runner 支援 Antigravity、Grok Build

**行為**：
- **Antigravity**：
  - agy_acp_server 預裝在 worker image（R8）。
  - 登入資料以 Docker secret `antigravity_auth` 傳入，內容是在別台電腦執行 `orbis-runner login antigravity` 後的資料夾壓縮檔。
  - 每個 Run 複製一份（R3）。
- **Grok Build**：Dockerfile 提供 build arg 安裝 CLI，登入資料以 `grok_auth` 傳入。
- **先驗證**：登入資料能不能在另一台機器沿用。不能沿用的 Agent 在文件中寫明不支援。

#### P4 `ghcr-images`：image 發布到 GHCR、Server image 瘦身

**行為**：
- **發布**：
  - 在本機以 `scripts/publish-images.ps1` 執行 docker buildx，建 server、runner、worker 三個 image（amd64、arm64）。GitHub 的 Windows、macOS runner 建不了 Linux image，CI 不加 Linux job。
  - DESKTOP.md 的發布步驟加上執行這個腳本。
  - 推到 `ghcr.io/<owner>/orbis-*:<版本>`，owner 取 repo 的擁有者。
- **compose**：預設改用這些 image，保留 build 的寫法。
- **Server image 瘦身**：建 image 時編譯 TypeScript 與 Web，執行層只放 production 依賴，不再用 tsx。

#### P5 `server-secrets`：Server 的 secret 改用 Docker secret

**行為**：
- DB 密碼、OAuth client secret、GitHub App 的 private key 與 webhook secret、session secret 改用 Docker secret。
- Server 支援 `<名稱>_FILE` 的環境變數慣例，名稱前綴從名稱常數取得。

#### P6 `caddy-example`：Caddy 反向代理與 TLS 範例

**行為**：
- `deploy/caddy/Caddyfile`：主網址加上 Preview 的 wildcard，Preview 的 wildcard 以 DNS-01 取得憑證。
- compose 加 profile `caddy`。
- INSTALL.md 加一節說明。

#### P10 `app-icon`：App 圖示

**行為**：
- SVG 原稿放在 `apps/desktop/build/icon.svg`，產出 ico、icns、png 與系統匣用的小圖示（macOS 用 template image）。
- 設計稿先給使用者看過再定稿。

#### P11 `release-channel`：Release notes 自動產生、pre-release 通道

**行為**：
- **Release notes**：依上一個 tag 之後的 Conventional Commits 產生，放進 draft Release。
- **pre-release**：
  - `v*-beta.*` 的 tag 建成 pre-release。
  - Desktop 設定加「接收預覽版」，開啟時 electron-updater 設 `allowPrerelease`。

#### P13 `best-of-n`：best-of-N

**行為**：
- **派工**：派工對話框可以選同時跑 2–4 個 Run，每個可以選不同的 Agent 與模型。
- **每個 Run 各自**：有自己的 Worktree 與分支（`-r<序號>`），各自跑 Verification。
- **比較**：
  - 全部完成 Verification 後，Task 進入比較畫面，並排顯示 diff、Verification 結果、費用與最後的回覆。
  - 選定一個後，這個 Run 進入 Review Gate；其他的取消，Worktree 照 P15 的保留期限處理。
- **並行上限**：每個 Run 都計入。

**契約**：
- Gate 種類加 `compare`。
- tasks 加 `primary_run_id`。
- API：
  - `CreateRunInput` 加 `variants[]`
  - `POST /api/tasks/:taskId/compare/choose { runId }`

**測試**：完整系統 e2e：兩個 Fake Agent 的 Run，選一個後走到核准。

#### P14 `live-browser`：即時觀看 Agent 的瀏覽器

**行為**：
- **畫面串流**：
  - browser 判定時，Runner 啟動 headless Chromium，以 loopback 開 remote debugging，Playwright MCP 用 `--cdp-endpoint` 連上。
  - Runner 以 CDP 的 `Page.startScreencast` 取得畫面，1–2 fps、寬 800 px，經 Runner 通道送到 Server，再推給 Web 的 Verification 分頁。
- **保存**：畫面不保存，證據仍是原本的截圖。

**契約**：協定的 binary 訊息加 screencast 的 kind；ws 加 `browser_frame` 訂閱。

#### P15 `worktree-retention`：Worktree 手動封存與保留期限

**行為**：
- **手動封存**：失敗或中止的 Run 可以在 UI 手動封存，沿用 RunControl `archive`。
- **自動封存**：Project 設定 `worktree_retention_days`，預設 14，到期由 Server 自動送 `archive`。
- **保留的分支**：還有未合併 commit 的分支照舊保留。

#### P16 `finish-completed`：結束（沒有變更）改成 completed

**行為**：
- 新增 RunControl `FinishWithoutChanges`：Runner 結束 Agent，不 push，Run 轉 `completed`。
- 之後照 Task 轉 Done 的規則封存，取代現在的 `cancel`。

#### P17 `ac-verify-detect`：AC 表單判斷 `[verify].commands`

**行為**：
- Server 經 GitHub App 讀 default branch 的 `.orbis/config.toml`，解析是否有 `[verify].commands`，快取 5 分鐘。
- 本機 Repo 讀不到，維持靜態警告。

**契約**：`GET /api/repos/:repoId/config-summary` → `{ verifyCommands: boolean | null }`。

#### P18 `needs-you-verification`：在 Needs You 直接做 Verification 的決定

Needs You 的 `stopped_run`（`verification_limit`）列直接提供「附意見再試」「略過」「中止」，沿用既有的 API。

#### P19 `task-note-ui`：Task note 的 UI

Task note 已存在 `task_notes` 表（Agent 的 `update_task_note` 與 Feedback Loop 的紀錄），新工作區介面在任務分頁加上 Task note 的時間軸。

#### P20 `ci-step-names`：CI 修正 prompt 中的步驟名稱

Feedback Loop 的 CI 修正 prompt 加上失敗的 job 與 step 名稱，經 `actions:read` 讀取。

#### P21 `slack-email`：Slack 與 email 通知

**行為**：
- **email 管道**：沿用後端缺口 `task-invites` 的 mailer。
- **Slack 管道**：
  - 用 incoming webhook。
  - 個人可以設定自己的 webhook。
  - Team 可以設定一個頻道，只送 Gate 與彙報週報。
- **偏好設定**：依事件類型與管道分別開關。
- **勿擾時段**：套用到桌面、email、Slack 這三種推送管道。

**契約**：
- notification_preferences 加 `channels`。
- members 加 `slack_webhook_url`（加密保存）。
- teams 加 `slack_webhook_url`。
- `apps/server/src/notifications/channels.ts` 加 `email`、`slack`。

### G 已知落差

#### G1 `agent-config-isolation`：Agent 設定隔離

**行為**：
- **隔離方式**：Runner 替每個 Agent 指定由 Runner 管理的設定目錄，不載入使用者全域的設定、MCP 與 Skill：
  - Claude Code：`CLAUDE_CONFIG_DIR`
  - Codex：`CODEX_HOME`
  - Antigravity、Grok Build：先查有沒有對應的環境變數
- **登入憑證**：另外連結或複製過去。
- **做不到的 Agent**：維持 AgentAvailability 的落差警告。
- **macOS 的 Claude Code**：認證存在 Keychain，換設定目錄後能不能沿用登入，要在煙霧測試中實機確認。

**測試**：Runner：設定目錄的環境變數與連結；煙霧測試（`scripts/smoke-agents.ps1`）加上「使用者全域的 allow 規則不生效」。

#### G6 `ci-app-allowlist`：CI App 白名單

Project 設定 `ci_app_allowlist`，填 GitHub App 的 slug；空的表示不限制。Feedback Loop 只採用清單內 App 的 check run。

#### G8 `desktop-feed`：Desktop 桌面通知套用個人設定

**現況**：Desktop 輪詢的是 `/api/needs-you`（`apps/desktop/src/main/notifications/needs-you.ts`），沒有用 `desktop-feed`，所以個人關掉的事件類型與勿擾時段都不生效，和 ARCHITECTURE §12.3 不一致。

**行為**：Desktop 改接 G9 的推送，收到的是 Server 已套用個人設定與勿擾時段的 `desktop_notification`；保留每 60 秒輪詢 `desktop-feed` 當備援。

#### G9 `push-updates`：輪詢改成推送

**現況**：Web 的 Needs You、看板、tasks、runs、留言、Draft、Runner 以 React Query 每 5 秒輪詢（`apps/web/src/api/resources.ts` 的 `POLL_INTERVAL_MS`）。

**行為**：
- `/api/ws` 加推送訊息，Web 收到後讓對應的 query 失效重抓。
- 輪詢改成每 60 秒一次的備援。
- Desktop 的 main 程序也開 `/api/ws`，帶 session cookie，Origin 用 Server 的 origin。

**契約**：`ws.ts` 加 `needs_you_changed`、`tasks_changed { projectId, taskIds }`、`runs_changed { runIds }`、`comments_changed { taskId }`、`desktop_notification { notification }`。

**測試**：Server：每種變化送出對應的訊息，而且只送給有權限的連線。Playwright：另一個使用者的修改在 2 秒內出現。

#### G10 `feedback-queue`：Feedback Loop 等 Runner 上線

前一個 Run 的 Runner 不在線上時，回饋照現有的暫存規則保留，那台 Runner 重新連上時才開修正 Run；超過 24 小時就放棄，在 PR 與 Task 上說明。

#### G13 `permission-scopes`：權限核准的範圍

**行為**：權限請求的選項加上兩個範圍：
- **這個 Run 都允許**：
  - 同一個 Run 中再遇到同一個請求就直接允許。
  - 指令以正規化後的完整字串比對，路徑以同一個檔案比對。
- **加進 Project 的規則**：
  - 只有 Admin 能選。
  - 寫進 Project 的權限規則，之後的 Run 和 `allow_commands` 一樣適用，參數檢查也一樣（§8）。
- 不做 LLM 判斷；`allow_commands` 的預設不放寬。

**契約**：
- 協定：`PermissionResponse` 加 `scope: once | run | project_rule`。
- `DispatchOffer` 加 `project_rules`。
- DB：新增 `project_permission_rules`（project_id、kind、pattern、created_by）。

**權限**：`project_rule` 要 `manage_permission_policy`。

**測試**：Runner：`run` 範圍在同一個 Run 中不再問；Project 規則的參數檢查和 `allow_commands` 相同（共用測試表）。

**文件**：修訂 ADR-0006；ARCHITECTURE §8。

### N 新功能

#### N2 `search`：全域搜尋與指令面板

**行為**：
- **搜尋範圍**：Task 的標題與描述、留言、Run 的 prompt 與最後回覆、對話的標題、Wiki 頁面、Skill。
- **指令面板**：Ctrl+K 開啟，可以搜尋，也可以執行動作（新增 Task、開對話、切換 Project、開設定）。
- **權限**：結果套用權限。

**契約**：
- Postgres 用 `pg_trgm` 建索引，中文用 trigram 做部分比對；英文另加 FTS 排序。
- API：`GET /api/search?q&types&projectId&limit`。

**測試**：Server 的中英文搜尋與權限過濾；Playwright 的指令面板。

#### N3 `templates`：Task 範本與 prompt 範本

**行為**：
- **Task 範本**：Project 的 Task 範本，包含標題格式、描述、AC、labels、優先度、類型；新增 Task 時選用。
- **prompt 範本**：Team 的 prompt 範本，可以設成個人或共用，在對話與派工的輸入框插入。
- **Wiki 頁面範本**：存在 Wiki 空間的「範本」資料夾，W7 使用。

**契約**：新增 `task_templates`（project_id、name、content jsonb）、`prompt_templates`（team_id、owner_member_id nullable、name、body）。

#### N4 `audit-log`：稽核紀錄

**行為**：
- **只能追加**：資料庫 trigger 拒絕 UPDATE 與 DELETE。
- **記錄的事件**：
  - Gate 決定、權限回覆
  - 成員與 Role 變更、彙報關係
  - 政策與 Project 設定的修改
  - 終端機開關
  - Skill 核准與使用
  - egress proxy 與 token（R9）
- **查詢**：Admin 可以篩選與匯出 CSV。

**契約**：新增 `audit_log`（team_id、actor_type：`member`｜`runner`｜`system`、actor_id、action、target_type、target_id、project_id、payload jsonb、created_at）；`GET /api/audit-log`。

**權限**：`manage_team`。

**測試**：Server：每種事件寫入；UPDATE 與 DELETE 被拒絕。

#### N5 `auto-dispatch`：依賴完成後自動派工

**行為**：
- **設定**：Task 可以設定自動派工，內容包括 Agent、在哪裡跑、模型、推理強度、權限策略。
- **觸發**：依賴都進入 completed 群組而且可以派工時，以設定者的身分派工。
- **失敗時**：派工失敗加入設定者的 Needs You。
- 和 A16 共用同一套規則。

**契約**：tasks 加 `auto_dispatch jsonb`；`PUT/DELETE /api/tasks/:taskId/auto-dispatch`。

#### N6 `blob-retention`：blob 保存期限可設定

**行為**：
- **設定**：
  - 環境變數 `<前綴>_BLOB_RETENTION_DAYS`，預設 90，前綴從名稱常數取得。
  - Team 設定可以覆寫，最少 7 天，0 表示永久。
- **套用範圍**：
  - 只套用到之後建立的 blob。
  - Wiki、Skill、彙報的附件不套用。

**契約**：teams 加 `blob_retention_days`；`apps/server/src/blobs/store.ts` 的 `BLOB_RETENTION_DAYS` 改成讀設定。

#### N7 `external-mcp`：對外的 Orbis MCP server 與個人 token

**行為**：
- **用途**：在 Orbis 以外直接用 Claude Code、Codex 時，也能讀寫 Task、Wiki、Skill。
- **連線**：Streamable HTTP 端點 `/api/mcp`。
- **認證**有兩種：
  - 個人 token：有範圍（唯讀或讀寫）與期限，只存 hash。
  - OAuth：authorization code 加 PKCE，支援 MCP 用戶端的動態註冊。
- **工具**：`list_tasks`、`get_task`、`create_task`、`update_task`、`comment`、`search`、`read_wiki_page`、`propose_wiki_edit`、`list_skills`、`get_skill`。
- **權限**：和本人在 Web 上相同。
- **速率限制**：每個 token 每分鐘 120 次。

**契約**：
- 新增 `personal_tokens`（member_id、name、hash、scopes、expires_at、last_used_at）與 OAuth 的資料表。
- API：`GET/POST/DELETE /api/me/tokens`。

**錯誤**：token 過期 → 401；範圍不足 → 403 `insufficient_scope`；超過速率 → 429。

**測試**：Server：兩種認證、範圍、速率；用 MCP 的 TypeScript SDK 寫的用戶端呼叫每個工具。

**文件**：ADR-0023；ARCHITECTURE §15。

## 分工

Agent 總數不超過 3 個（含協調者），每個 worker 一個獨立的 Git worktree，用 Orca 派工。每一波：

1. **契約 worker**：做該波的契約 PR，包含協定、api-contract、migration、ADR、GLOSSARY、ARCHITECTURE、Fake Agent 劇本。CI 通過、協調者審完就合併，合併後把 ADR 清單給使用者。
2. 契約合併後，兩個 worker 平行做完：
   - **Runner＋Desktop worker**：`crates/runner`、`crates/fake-agent`、`apps/desktop`、`deploy/` 的 Runner 部分。
   - **Server＋Web worker**：`apps/server`、`packages/github`、`apps/web`、`deploy/` 的 Server 部分。
3. 兩個 worker 都完成後補該波的完整系統 e2e，再開下一波的契約 worker。
